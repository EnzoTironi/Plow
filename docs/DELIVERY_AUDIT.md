# iMessage delivery audit — 2026-09-19

The intermittent replies are reproducible transport and instruction-contract
defects. They are not evidence that the Google account remains disconnected.
This audit records the `release-50336ee` behavior before the delivery repair.
The follow-up implementation is described in `RUNTIME.md`; release and live-test
status must be checked separately from this historical evidence.

## Confirmed failures

### 1. Valid final answers are discarded

`image/plugins/zoen-face/quiet.py:97` replaces the Plow adapter's normal `send()`.
Apart from the special credit notice, **every** call is dropped, including a
normal final answer and command output. Delivery therefore depends on the model
using `plow_send_sequence` for every answer.

The pinned Plow adapter supplies a channel instruction telling the model to write
its answer last, and promises that this final message reaches the chat. Zoen's
own persona and skill instead require tool-only delivery. The Zoen override
invalidates the platform's promise. This is an instruction conflict backed by
an unconditional code path, not just a wording issue.

In an isolated container using the exact running image, with temporary state and
only loopback HTTP fixtures:

| Same final answer | Actual message POSTs | Adapter result |
| --- | ---: | --- |
| Zoen's current wrapper | 0 | failed, suppressed |
| Original Plow `send()` | 1 | success |

The live iMessage test is consistent with this: generic Google verification
requests and `/status` produced no visible answer, whereas requests explicitly
requiring `plow_send_sequence` produced the connection and verification results.
Raw cloud turn logs were not available, so this audit does not claim to attribute
every missing live message to a specific generated final answer.

### 2. An opening can be mistaken for the completed answer

The pinned Plow `send_sequence()` marks `turn.reply_delivered = True` on successful
delivery. Its `_message_guard()` then suppresses ordinary trailing prose as a
duplicate. It cannot distinguish an opening status from a completed answer.

A second isolated experiment restored the original Plow `send()`, sent an opening
through the real `send_sequence()`, and then submitted a distinct final answer.
Only the opening was posted; the final send still reported success. Consequently,
simply removing Zoen's blanket filter is insufficient. Reception POSTs do not set
this flag, but the main agent's fallback opening uses `plow_send_sequence`.

### 3. Reactions are selected by a narrow keyword rule

`presence.py:35` selects `like` using regular expressions, not the model. Direct
tests returned:

| Request | Reception reaction |
| --- | --- |
| `conecta meu Google` | none |
| `confirme a conta Google conectada` | none |
| `connect my Google account` | none |
| `pode conectar meu Google?` | like |

The statusline wording is generated by the model. The reaction is still a
deterministic heuristic. Its input does not include conversational history.

### 4. Status and reaction delivery are conflated

`presence.py:202` stores the statusline's outcome whenever a statusline exists,
discarding the independent reaction outcome. Reproduced combinations:

| Actual status | Actual reaction | Stored result | Instruction to main agent |
| --- | --- | --- | --- |
| sent | failed | sent | Do not send another status or reaction |
| failed | sent | failed | No reception note; the agent may repeat the reaction |

The send claim is also represented by a single `pending` state. Pending or
uncertain delivery suppresses replay of both components. Preserving ambiguous
sends is appropriate; treating two separate effects as one is not.

### 5. Five seconds is a target, not an enforced budget

There is a 0.3-second draft delay, a six-second generation timeout, and a separate
three-second send timeout. The two-second burst window overlaps generation, but
does not cap its duration. `annotate()` can hold the main handoff for up to nine
seconds while waiting for reception. The status path can therefore delay both
the opening and the start of the actual work.

A controlled model delay of 5.3 seconds, still below its configured timeout, plus
a 0.3-second send produced **5.937 seconds before main handoff**. There was no
external network in this experiment. A timeout/failure produces no canned status;
the main agent is asked to supply an opening, which re-enters the delivery
conflict described above.

Prior live measurements in `RUNTIME.md` also missed five seconds in some cases
and recorded one long delay before the agent received the message from Plow.
Those are previous samples, not measurements of the current incident. Timing
must distinguish phone send, Plow creation, agent receipt, provider acceptance,
and appearance on the phone.

## Google: account access and conversation delivery are different states

The earlier Worker failure was real: workerd rejects `redirect: "error"` before
contacting Google's token endpoint. `21360da` changed this to `manual` with
explicit rejection of redirects. That fix is deployed and covered by a workerd
test. The public configuration currently reports configured / unverified.

After consent, the cloud agent reported saved credentials and then, through an
explicit message-tool response, successful renewal in a new process, identity
verification, and one minimal Calendar read. This evidence comes from the live
iMessage response, not independently retrieved raw VM execution logs. Other
Google services and a complete VM restart were not tested with this account.

Remaining conversation weaknesses:

- Login-link and completion events are handed back to the model. Their visible
  delivery still depends on the broken output contract above.
- `google_connections.dispatch()` prevents a second **active** login, but does
  not short-circuit a new `connect` when adequate saved credentials already exist.
  Checking status first is currently only an instruction. A repeated connect can
  unnecessarily create another consent flow.
- The latest job's status overwrites the account status field, even after that
  job has finished. Saved account health and the latest authorization attempt
  should be separate fields.
- Internal connection events receive another owner-turn prompt without a
  reception note. The generic “first tool is the statusline” instruction can
  cause another opening. This is a prompt risk, not a measured duplicate count.

The new reception path changes when the main model is told to skip its opening.
That plausibly exposes the older final-answer suppression more often; its effect
on real failure frequency has not been measured. There is no evidence here that
changing Luna alone would solve these defects.

There is also stale onboarding text: `skills/zoen/SKILL.md` says both that reception
may precede the introduction and, later, that nothing may precede it. The current
persona/bootstrap use the newer rule. This contradiction should be removed, but
it does not explain every silence after onboarding.

## Repair order and acceptance criteria

1. **Repair the delivery contract.** Final answers must have a reliable automatic
   path. Track openings, progress and final answers separately. Keep native
   authorization, group privacy, duplicate suppression and diagnostic filtering.
   An opening must never satisfy final delivery; a delivered final must not replay.
2. **Unify instructions.** Reconcile the Plow channel prompt, Zoen persona and
   skill. Remove contradictory onboarding and tool-only-final rules. Preserve
   Zoen's voice. Internal connection events should not start another greeting.
3. **Repair reception state and timing.** Store separate status/reaction outcomes,
   use an explicit total latency budget, and keep slow reception from blocking
   the main work. Give contextual generation enough conversation context. Keep
   generated wording; do not reintroduce canned acknowledgements. Report missed
   deadlines rather than claiming the five-second target is guaranteed upstream.
4. **Make connection reuse explicit in code.** Reuse valid existing grants for
   the same account and scopes; request consent only when needed. Separate
   connection health from the latest attempt and reliably deliver completion.
5. **Test the visible outcome.** Exercise a normal model final, an opening followed
   by a final, explicit sequence plus trailing prose, each mixed receipt outcome,
   a slow model, a busy turn, burst corrections, and OAuth completion. Finish with
   real iMessage tests without instructing the model which send tool to use.

Existing reception tests use fast model/send fixtures; the image integration test
replaces the main message handler. The quiet-filter test explicitly expects normal
text to disappear. Passing those tests therefore does not establish reliable
end-to-end replies. The cloud instance and its connected account were preserved
throughout this audit.

The seven isolated diagnostic scenarios above ran against the deployed image.
The existing targeted suite was also rerun: **33 passed in 2.99 seconds**
(`test_presence.py`, `test_statusline.py`, `test_zoen_face_quiet.py`). These passing
tests coexist with the reproduced defects; they are not a delivery sign-off.
